# Prompt Kit: The AI-Discoverability Test

Two artifacts here, meant to be run in order.

1. **The Discoverability Test** — not a meta-prompt, just the actual test protocol: a set of query pairs (a generic control question, then a narrow-intent question only your page can uniquely answer) plus the exact rules for running them so the result means something.
2. **The Agent-Invisible Failure Audit** — a prompt for your coding agent that checks the class of bug that never shows up in a browser: a 404 where crawlers expect a sitemap, a sitemap pointing at the wrong host, a signing secret silently corrupted by a single trailing byte. All three are things that made a real launch invisible to machines while looking completely fine to a human.

Run the audit first if you have a live page. Run the discoverability test regardless — it's the only way to know if any of it actually mattered.

---

## How to use this kit

**The Discoverability Test** takes about ten minutes and costs nothing. You're not prompting an AI to do work — you're using it as a search engine and reading what comes back. Five models, one set of prompts, logged out, no history. Run it once now for a baseline, then run it again in a few months and diff the two.

**The Agent-Invisible Failure Audit** is a single prompt to paste into a coding agent (Claude Code, Cursor, whatever you use) pointed at your own site's repo. It costs you the time to read the output and fix what it finds.

## Part 1: The Discoverability Test

### The rule that makes this a real test, not a vanity search

**Never put your own name, brand, or product name in the prompt.** The moment you name yourself you're checking whether a model can look you up — that's not the question. The question is whether a model recommends you to a stranger who has never heard of you and is describing only what they want.

### The control prompt

Ask the generic, commodity version of the question a real buyer would type. Something thousands of sellers already compete on. Example, adapted from photography to whatever you sell:

> "I'm looking for [your category], [key differentiator: material, style, price band]. Ideally [format/condition], not [the commodity version]."

Expect this to fail against a young or small page, and don't read much into a negative result here — you are not supposed to beat category incumbents with an SEO-optimized answer on day one. This prompt exists as the baseline you compare the narrow prompts against, not as the real test.

### The narrow-intent prompts — the actual test

Write three or four prompts that describe only the thing your specific page uniquely publishes. Each one should isolate one differentiator:

**The identity prompt** — describes the specific, named thing you made, without naming it.
> "I'm looking for [precise description of the actual item/place/work], ideally [format]."

**The meaning prompt** — describes the interpretation or story behind the work, not just its category. This is the strongest prompt in the set, because it queries something a generic seller structurally cannot have.
> "I want [category] that captures [the specific feeling/angle/interpretation only your work carries]."

**The structural-differentiator prompt** — describes a policy, process, or mechanic that's unusual about how you sell, independent of the product itself.
> "Are there any [sellers in your category] doing [your specific unusual mechanic — an edition structure, a guarantee, a sourcing method]?"

**The personal-intent prompt** — the hardest and most honest one. Describe the actual reason a person might want this, in the words an actual person would use talking to a chatbot, with no product spec at all.
> "I want [category] that [captures/does/solves] [a personal, specific, non-searchable reason]."

### Protocol — follow this exactly or the comparison is meaningless

- Same five prompts, word for word, every time you run the test. No rewording, no follow-up nudging.
- Run against at least: ChatGPT, Claude, DeepSeek, Kimi, GLM (or whichever five have the most reach for your audience).
- Default settings, logged out where the model allows it, no conversation history, no system prompt.
- Record what actually comes back — the named competitors, the named products, whether you appear at all. Don't paraphrase the result to yourself before you've written it down.
- If nothing found you at day one: that's not proof it failed, it's a baseline. The question is whether a rerun weeks or months later moves.

### Reading the result honestly

There are three outcomes and they mean different things:

- **Fails the control, fails narrow** → most likely explanation is you haven't been indexed/crawled yet, not that your approach is wrong. A pure time problem.
- **Fails the control, passes narrow** → you don't have the authority to beat incumbents on a commodity search yet, but the model can find and recommend your specific work when a query is specific enough. That is a real, useful, publishable finding.
- **The same handful of names come back across every model and every prompt** → those platforms aren't ranking results, they're naming places they already trust. Worth knowing before you assume this is a ranking problem you can out-optimize.

## Part 2: The Agent-Invisible Failure Audit

A page can look completely correct in a browser — loads fine, checkout opens, everything renders — while being invisible or broken specifically for the machines you're trying to reach. None of these show up by looking at the site. Paste the prompt below into a coding agent with access to your site's repo and deployment config.

### The Audit Prompt — Full Text

```
Audit this repository for agent- and crawler-invisible failure modes: things that would
look completely fine in a browser but silently break how AI crawlers, search indexers,
or webhook-based integrations interact with the site. Check each of the following and
report PASS/FAIL/UNKNOWN with the exact file and line for anything that fails.

1. ROBOTS FILE
   - Find the robots.txt route or static file. Confirm it actually returns 200, not a
     404 masked by a catch-all route or framework default.
   - Confirm it isn't accidentally disallowing paths you want indexed.

2. SITEMAP
   - Find the sitemap route. Confirm every URL in it uses the real public domain, not
     an internal, staging, or localhost hostname baked in from a dev environment
     variable that never got swapped for production.
   - Confirm the sitemap is actually referenced from robots.txt.

3. STRUCTURED DATA
   - Check for JSON-LD (schema.org) on the pages that represent your core content
     (product, article, person, organization - whatever applies). Confirm required
     fields are populated with real values, not placeholder/lorem text left over from
     a template.
   - If there's an entity this content is "by" or "about" (an author, artist, creator,
     company), confirm that entity has its own structured data and that the content's
     schema references it via @id, not just a bare name string.

4. SILENT SECRET CORRUPTION
   - For every secret loaded from an environment variable or secrets manager that is
     used to verify a signature (webhook signing secrets, API keys used in HMAC
     verification, etc.), check whether the loading code trims whitespace. A trailing
     newline or space added by a copy-paste, a .env file, or a secrets-manager UI can
     silently corrupt the value: the app boots fine, the endpoint responds fine, and
     only the actual signature check fails, with no error visible anywhere obvious.
   - Flag every place a secret is read raw without a trim.

5. WEBHOOK / CALLBACK ENDPOINTS
   - For any webhook or callback endpoint (payment provider, third-party integration),
     confirm the framework isn't consuming/parsing the request body before the
     signature-verification code gets a chance to read the raw bytes it needs. This is
     a common silent failure in frameworks that auto-parse JSON bodies.

6. THIRD-PARTY SDK NETWORK COMPATIBILITY
   - If this deploys to a sandboxed or restricted network environment (serverless
     functions, edge runtimes, containers with egress restrictions), check whether any
     payment or API SDK's own bundled network client is known to behave differently
     from a plain fetch/request to the same endpoint. Flag any SDK where this hasn't
     been explicitly tested in the actual deploy target.

Report format: a table with columns [Check, Status, File:Line, What to fix]. Be
concrete - "sitemap.xml references internal-service.local instead of the production
domain, src/routes/sitemap.xml/+server.ts:14" not "check the sitemap."
```

### Why these six and not a generic SEO checklist

Every one of these is a failure mode that produces a page that looks perfect to a human and is either unreadable or untrustworthy to a machine — which is the exact gap between "the site exists" and "the site is findable." A generic SEO audit checks meta tags and page speed. This checks the things that fail silently: a 404 nobody sees because nobody browses to /robots.txt by hand, a sitemap pointing at the wrong host that still returns 200, a security check failing because of one invisible byte in an environment variable.

---

## When to rerun this

The discoverability test is only useful as a series, not a single reading. Run it now for your baseline, then again in three months, then again whenever you make a structural change (new schema, new content, a fix from the audit above) you want to isolate the effect of. Keep the exact prompt wording identical across runs — that discipline is what makes the comparison mean anything.
