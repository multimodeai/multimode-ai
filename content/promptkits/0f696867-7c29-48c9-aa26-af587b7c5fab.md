# The Savings-Claim Audit Kit

**5 prompts for checking any AI tool's "we saved you X" number — and deciding what to actually do about your own bill.**

The measurement tooling for this is free and MIT: `github.com/multimodeai/token-tax-kit`. It tells you what happened. This kit is the part that isn't code — how to read the result, how to audit a claim before you install anything, and what to do about the lever that actually moves your bill.

---

## Before you start: the one mechanic everything here depends on

The model forgets everything the instant it answers. So every question re-sends the entire conversation from the start.

Your bill is not what you gave it. Your bill is **how many times it got read back**.

Every prompt below is an application of that single fact.

---

## Prompt 1 — Audit any tool's savings claim before installing it

Use when a tool, plugin, or extension claims a percentage reduction in tokens or cost.

```
I'm evaluating a tool that claims it reduces my AI coding costs. Here is its
claim and, if available, its documentation:

<paste claim / README / blog post>

Interrogate the claim on these axes and answer each one separately. Where the
source doesn't say, write "not stated" rather than inferring.

1. COUNTERFACTUAL. Does the reported number come from measured billing, or
   from the tool's own estimate of a session that never happened? Quote the
   exact wording that tells you which.
2. DENOMINATOR. Percent of what? Total tokens, input tokens, tokens of one
   specific type, or dollars? These give wildly different numbers for the
   same event.
3. SECOND-ORDER EFFECTS. Does the intervention ever cause the model to need
   an extra turn (a refusal, a retry, a narrower re-request, a clarification)?
   If yes, is the cost of those extra turns included in the reported figure?
4. TOKENS VS DOLLARS. Are the tokens it saves cheap tokens or expensive ones?
   Cached input bills at a fraction of fresh input; output bills several times
   higher than input. A large token saving in the cheapest category can be a
   rounding error on the invoice.
5. INDEPENDENT CHECK. Has anyone outside the vendor measured this against a
   real bill? What did they find?

Finish with: what would have to be true for this claim to hold on MY workload,
and what is the single cheapest test that would falsify it.
```

**What good output looks like:** a tool that survives all five is worth installing. Most claims die on 1 or 3.

## Prompt 2 — Decide whether a size gate is worth it for your repo

Run `token-tax ceiling --project <your repo>` first. Then:

```
Here is the ceiling output from my own repo - the theoretical maximum a
file-read gate could save me, computed from sessions I actually ran:

<paste ceiling output>

And here is my report output:

<paste report output>

Work through this and give me a straight recommendation:

1. What share of my bill could a read gate touch AT BEST, in dollars per
   month at my current usage? Use the "counted every re-read" number, which
   is the one that favours the gate.
2. My gate will sometimes refuse a read the model genuinely needed, costing
   an extra round trip. Using my average context size and output per turn,
   what does ONE extra round trip cost me?
3. How many wrong refusals per month would it take to wipe out the best-case
   saving from (1)?
4. Given (3), is installing a gate rational for this repo? Answer yes or no
   before you explain.

Do not soften the answer. If the honest answer is "this is not worth
installing", say that.
```

**Why this is the load-bearing prompt:** on every repo I measured, the answer to 4 was no. If yours says yes, you have found something I did not, and I would like to hear about it.

## Prompt 3 — Find the extra-turn tax in your own transcripts

The failure mode that makes bills go up is invisible unless you look for it.

```
I want to find where my AI coding sessions are spending turns instead of
tokens. Using the session data I'm pasting below:

<paste report output, plus any gate log>

Identify:
1. Places where one logical request became multiple round trips - a refusal
   followed by a retry, a truncated read followed by a continuation, a
   search followed by a narrower read of the same file.
2. For each pattern, estimate the extra cost, remembering that every round
   trip re-sends the whole conversation.
3. Rank the patterns by total cost, not frequency.
4. For the top 2, tell me whether the fix is a config change, a habit
   change, or nothing (some round trips are the model working correctly).

Be explicit about which of these I can actually control.
```

## Prompt 4 — The session-lifecycle audit (the 6.6x lever)

This is the one that matters most, and the one no tool sells you.

Measured across 8 real sessions: a question in a fresh chat cost $0.07. The same question in an established chat cost $0.43. That is 6.6x, and it is paid up front — it plateaus rather than compounding, because compaction caps it.

```
I pay roughly 6.6x more per question in a long-running session than in a
fresh one, because the whole conversation is re-sent every turn. I want to
decide deliberately when that's worth it instead of defaulting into it.

Here's a description of how I actually work with an AI coding assistant:

<describe: typical session length, whether you start fresh per task or keep
one session open, what context you rely on carrying over>

Give me:
1. Which parts of my carried context are genuinely load-bearing (the
   assistant would make a worse decision without them) versus inertia
   (it's just still there).
2. A concrete rule for when to start a fresh session, stated as a trigger I
   can notice in the moment - not "when it gets long."
3. What I should write down or hand off at that boundary so a fresh session
   isn't worse, and what is NOT worth carrying.
4. The honest counter-argument: where starting fresh would cost me more than
   6.6x in mistakes, rework, or re-explanation.

I want (4) taken seriously. Cheaper is not automatically better.
```

## Prompt 5 — Write the falsification test before you believe your own result

For when you measure something yourself and it agrees with what you hoped.

```
I measured something on my own system and got a result I like. Before I act
on it or publish it, attack it.

My claim:
<state it in one sentence>

My method:
<how you measured>

My numbers:
<paste>

Do this:
1. Name the assumption in my method that, if wrong, would most change the
   result. Not the most likely to be wrong - the most CONSEQUENTIAL.
2. Is my number flattering to a conclusion I already wanted? If so, which
   part of the method is doing that work?
3. Give me one cheap test that would falsify my claim if it's wrong.
4. Rewrite my claim with the honest scope attached - what it covers, what
   it does not, and the n.
```

**Why this is in the kit.** I ran it on myself and it saved me from publishing a number that was 53x too large. My first ceiling calculation assumed a file read into a session stays in context forever. It produced $722 — 47% of my bill, a spectacular finding. It was also wrong: Claude Code compacts, so a file read at turn 100 is not still there 4,900 turns later. Bounded properly, it was $13.56.

A number that flatters your thesis deserves more scrutiny, not less. That applies to mine as much as to the vendor's.

## The four commands, for reference

```bash
token-tax report   --project <repo>   # what actually happened
token-tax ceiling  --project <repo>   # the most a gate could ever save
token-tax snapshot before.json        # ... enable gate, do comparable work ...
token-tax snapshot after.json
token-tax compare before.json after.json
```

`compare` prints the change in turn count next to the change in tokens, deliberately. If turns went up, a token saving on reads is being paid for somewhere else. That is the entire failure mode in one line of output.
